# Windows 命令沙箱方案

参照 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 的 `packages/sandbox/sandbox-windows-acl`（MIT 许可，读的是 2026-11-18 的 `2e39e70496`）。下面"它的做法"和"它记下的代价"两节是它的文档和源码里写的，**我没有在本机验证过**；"搬到这里"之后是我的设计。

## 结论

能做，而且它的路子是目前已知最不打扰用户环境的一种：不建新账号、不要管理员权限、不装驱动。但有三样代价要先想清楚，所以建议**先花一两天做验证，再决定做不做**：

1. **它会永久改洞府的权限。** 第一次用时给洞府目录加两条权限项和一个"低完整性"标签，之后一直留着。大目录第一次要几十秒。
2. **沙箱里 Node 派生子进程会失败。** 用管道接子进程输出的写法（`spawn(..., { stdio: 'pipe' })`）在沙箱里报 EPERM。不少前端工具链这样干，所以在 JS 项目里可能频繁要"出沙箱"。这一条最可能让它不实用。
3. **只管写和删。** 读文件、联网不受限，和现在 Linux、macOS 上一样。

## 它的做法

用的是 Windows 自带的"受限令牌"，一共五步。任何一步的系统调用失败都直接报错，绝不退回成不受限地运行。

**一、给洞府一个专属身份。** 把洞府的规范路径做 SHA-256，取前 8 字节拼成一个 SID：`S-1-4-<x>-<y>`。这个 SID 不对应任何账号，只是一张"通行证"的编号。同一处洞府永远得到同一个编号。临时目录另算：每次新建一个随机的私有临时目录，用它的路径另派生一个 `S-1-4-<x>-<y>-1`。

**二、在目录上登记这张通行证。** 对洞府目录调一次 `SetNamedSecurityInfoW`，同时做三件事：

| 改动 | 内容 | 继承 | 作用 |
|---|---|---|---|
| 允许项 | 通行证 SID，掩码 `0x110156`（写、追加、改属性、删除、删子项） | 子目录和文件 | 持证者可写可删 |
| 拒绝项 | Everyone，`FILE_DELETE_CHILD`（`0x40`） | 只到子目录 | 堵住"靠父目录的权限删文件"这条旁路 |
| 完整性标签 | 低（`S-1-16-4096`），禁止向上写 | 子目录和文件 | 让低完整性的进程写得进来 |

登记前先读现有权限，三样都已原样存在就跳过，所以只有第一次慢。读改写全程持一把按路径的文件锁，防止两个进程互相覆盖。

**三、造一个受限令牌。** 复制当前进程的令牌，调 `CreateRestrictedToken`，标志 `DISABLE_MAX_PRIVILEGE | WRITE_RESTRICTED`，限制名单是：登录会话 SID、Everyone、洞府通行证、临时目录通行证。`WRITE_RESTRICTED` 的意思是：写类访问要查两遍，用户本来的身份查一遍，限制名单查一遍，两遍都过才放行；读不受影响。

**四、把令牌降到低完整性**（`SetTokenInformation(TokenIntegrityLevel)`），并在令牌的默认权限里加一条通行证的完全访问。前者使它只能写带"低"标签的目录；后者使它自己新建的匿名管道之类的对象自己能用。

**五、用这个令牌起进程。** `CreateProcessAsUserW`，先挂起，放进一个"关句柄即杀全部"的作业对象，再恢复。把 `TMP`、`TEMP` 指到那个私有临时目录。进程退出后撤销临时目录的登记并删掉它；洞府的登记留着。

为什么要标签加拒绝项两层：只靠第三步的话，Windows 还允许凭父目录的"删子项"权限删文件，这条不经过限制名单，于是沙箱里的 `del` 能删洞府外的文件。标签堵住了洞府外；拒绝项堵住了"从一处洞府删另一处洞府"。

## 它记下的代价

这些是它文档里"已知限制"的部分，我按对我们的影响排序。

- **用管道的孙进程起不来。** libuv 的管道是命名管道，受限令牌打不开客户端那一头。继承或忽略输出的可以，PowerShell 自己的管道可以。
- **权限改动是永久的。** `icacls` 撤不掉（报 1332，SID 对不上账号），只能用它自己的撤销函数。洞府改名后旧登记成了残留。
- **"低"标签会放宽别的东西。** 同一用户下任何低完整性进程（比如别的软件的沙箱进程）从此都能写这处洞府。
- **第一次登记要遍历整棵目录树。** 大洞府几十秒。
- **洞府必须是当前用户所有、且有完全控制权。** 只有"修改"权限的目录会登记失败。FAT 卷不行。
- **不能用 `CREATE_NO_WINDOW`。** 受限令牌下带这个标志的进程在加载 DLL 时就死（`0xC0000142`）。它的办法是让子进程共用宿主的控制台，用 `SW_HIDE` 藏窗口。
- **WMI 用不了。** `Get-ComputerInfo`、CIM 系列命令在沙箱里失败。
- **硬链接是漏洞。** 洞府里一个文件若在洞府外还有硬链接，外面那个也跟着可写。pnpm 的仓库大量用硬链接，所以它没法拒绝硬链接，只是如实标成"部分生效"。
- **别的沙箱工具动过的文件可能读不了。** 权限里带 AppContainer 包 SID 的文件，低完整性令牌打不开。
- **只读模式下 PowerShell 进受限语言模式。** 我们只做"可写洞府"一种，不受影响。

## 搬到这里

### 形状

和 macOS 一样用"外面套一个启动器"的形状，这样 [tools.rs](../crates/odg-core/src/tools.rs) 里跑命令、读输出、超时、后台任务那一套都不用动：

```
odg（界面或命令行）
  └─ odg-sandbox-run.exe --workspace <洞府> [--write <目录>]... -- pwsh.exe -Command ...
       └─ pwsh.exe（受限令牌，在作业对象里）
```

启动器是 `odg-core` 里新增的一个小可执行文件。它做上面的三、四、五步，把自己的标准输入输出原样传给子进程，等它结束，把退出码带回来。启动器被杀时作业对象关闭，整棵进程树跟着结束，比现在的 `taskkill /T` 更可靠。

第二步（登记目录）不放在启动器里，由 odg 主进程在第一次需要时做：它慢、要请示、而且只做一次。

### 要改的地方

| 文件 | 改动 |
|---|---|
| `crates/odg-core/src/sandbox/windows.rs`（新） | 派生 SID、登记和撤销、造令牌、起进程。用 `windows-sys`（已在依赖树里）。 |
| `crates/odg-core/src/bin/odg-sandbox-run.rs`（新） | 启动器的入口：解析参数，调上面的函数，失败时打印 `odg-sandbox-run: <原因>` 并以 127 退出。 |
| [sandbox.rs](../crates/odg-core/src/sandbox.rs) | `support()` 在 Windows 上返回"受限令牌"或原因（找不到启动器、洞府不在 NTFS 上）。`command()` 返回启动器的命令行。 |
| [tools.rs](../crates/odg-core/src/tools.rs) | 走启动器时不加 `CREATE_NO_WINDOW`（或按验证结果换别的办法藏窗口）。把 127 加"odg-sandbox-run:"认作沙箱坏了，而不是命令失败。 |
| [policy.rs](../crates/odg-core/src/policy.rs)、[agent.rs](../crates/odg-core/src/agent.rs) | 新增一条请示：第一次在某处洞府用沙箱前，问一次"要给这个文件夹加沙箱标记"。准了记成长期许可。 |
| [Transcript.tsx](../src/components/Transcript.tsx)、[Settings.tsx](../src/components/Settings.tsx) | 这条请示的文案；设置页里列出登记过的洞府，各带一个"撤销标记"。 |
| `src-tauri/tauri.conf.json` | 把启动器作为附带的可执行文件一起打包。 |

### 和另外两个系统不一样的地方

- **临时目录是私有的。** Linux、macOS 上放行整个系统临时目录；Windows 上每条命令一个随机目录，`TMP`、`TEMP` 指过去，用完删掉。
- **"另外准许写入的目录"先不支持。** 给 `~/.cargo` 这种目录打"低"标签等于把它开放给所有低完整性进程，而且要遍历一大棵树。先在设置页上写明 Windows 不支持，等有需求再议。
- **独立工作树的分身**要额外登记原仓库的 `.git` 目录，否则它提交不了。用同一个洞府 SID。

### 测试

- 派生 SID、拼命令行这类纯函数：单元测试，三个系统都跑。
- 真沙箱：放在 `crates/odg-core/tests/sandbox_windows.rs`，用 `CARGO_BIN_EXE_odg-sandbox-run` 找到启动器。内容和现在 Linux 上那条一样：洞府内能建、改、移、删；洞府外不能写、不能删、不能移出去；嵌套的子进程也一样；再加一条"两处洞府互相删不了"。本机和 CI 的 Windows 任务都能真跑。
- 失败即拒绝：造令牌或登记的任一步失败时，命令没有被执行。
- 端到端里现有的"沙箱开关是禁用的"那条检查要改成相反的。

## 分步

每一步都能单独验证，前一步不过就不往下走。

**第一步：验证（一两天，不进主分支）。** 写一个最小的启动器，手工登记一个临时目录，在这台机器上回答下面几个问题：

1. 从没有控制台的界面进程起启动器，再起 `pwsh`，会不会弹窗口、会不会 `0xC0000142`？哪种标志组合可行？
2. 沙箱里这些能不能跑通：`cargo build`、`cargo test`、`git commit`、`pnpm install`、`pnpm test`、`pnpm build`。哪些因为管道的限制失败？
3. 给这个仓库（约几万个文件，含 `target` 和 `node_modules`）做第一次登记要多久？
4. 撤销之后，目录的权限和标签是否回到原样？

第 2 问决定这件事值不值得做。如果 JS 工具链大面积失败，就停在这里，把结论记进路线图。

**第二步：核心。** `windows.rs`、启动器、`support()` 和 `command()`，加上面的集成测试。此时还没有请示，只在测试里用临时目录。

**第三步：请示和撤销。** 首次登记前的请示、设置页里的撤销、失败时给分身的提示（沿用现在的"可以请示出沙箱"）。

**第四步：打包和端到端。** 启动器随应用打包；端到端加一段真实的沙箱内命令。

## 没把握的地方

- 它文档里的每一条限制我都没复现过。尤其"管道孙进程失败"的范围，它只说了 libuv，实际影响面要靠第一步的第 2 问来量。
- 它说 `CreateProcessAsUserW` 传环境块会失败，要改用先设环境变量再传空。这看着像它用的 FFI 库的问题，Rust 里多半没有，但没试过。
- 它的验证环境是 Windows 11 26200。Windows 10 上的行为它没提。
- 登记是永久改动用户的文件夹。即使做了请示和撤销，这也是我们第一次改洞府内容以外的东西，出了问题不好收拾。它为此专门写了一个四万多字节的诊断修复脚本，可见这块容易出事。
