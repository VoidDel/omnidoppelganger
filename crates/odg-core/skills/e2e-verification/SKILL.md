# 端到端验收

只跑单元测试只能说明代码“编译通过、局部逻辑对”，端到端验收用来确认**真实用户能完整走通流程、界面没画歪、控制台和网络没有暗错**。

## 什么时候跑

- **条件触发，不必每次小改动都跑**：涉及 UI 布局、交互流程、表单/弹窗/路由、关键主链路或跨模块集成改动时启用。
- 纯内部重构或纯算法单测能完全覆盖的改动，跑单测即可。

## 按技术栈选驱动

- **Web / 前端 / 全栈 / Electron / Tauri 前端**：优先使用已接入的浏览器法器（如 `playwright` 或 `chrome-devtools` MCP）；若项目自带 E2E 脚本（如 `pnpm e2e`、`npx playwright test`），优先复用。
- **CLI / 后端 API / 服务**：用后台命令启动服务或直接运行编译后的二进制，在独立临时目录里发真实请求/命令并检查退出码、输出与落盘结果。
- **无浏览器法器时**：明确告知用户可以在「法器」页一键开启 **Playwright** 或 **Chrome DevTools**，不要假装已经点过页面。

## 标准验收流程

1. **隔离并启动被测物**
   - 用后台命令启动开发服务器或被测服务，等待端口真正就绪（检查日志或端口监听）后再开始操作。
   - 不要污染用户的真实配置或生产数据；尽量用临时目录或测试账号。

2. **先看结构再操作（定位纪律）**
   - 浏览器场景先取页面无障碍树快照（snapshot），按 role、按钮文字、label 或稳定的 `data-testid` 操作，不要盲猜像素坐标。
   - 覆盖真实路径：打开页面 → 输入/粘贴/点击 → 状态变化 → 刷新或回退确认持久化。

3. **三件套同步核验**
   - **页面/结果状态**：断言可见文本、元素状态或落盘文件确实符合预期。
   - **控制台错误**：检查 browser console 是否出现未捕获异常、React/Vue 警告或 Hydration 错误。
   - **网络请求**：检查是否有意外的 `4xx` / `5xx` 或挂起请求。

4. **截图并做视觉审查**
   - 在关键节点截图（初始态、交互后、弹窗/抽屉态、边界或空状态），并亲自查看返回的截图。
   - 重点排查：布局错位、元素重叠遮挡、文字截断溢出、暗/亮色主题对比度异常、白屏或骨架屏卡死。

5. **闭环修复与清理**
   - 发现任何问题：修代码 → 刷新或重启复测 → 重新截图确认已解决。
   - 验收结束后**停止你启动的后台服务**，清理临时测试文件。

## 汇报格式

- 列出验证的环境与命令（启动了什么、测了哪个地址/二进制）。
- 逐条给出关键场景的通过/失败状态、控制台与网络检查结果、以及截图里观察到的视觉细节。
- 如果有未能覆盖的场景（例如缺少某个真机/凭据/法器），明确说明。
