# 审查改动

审查要找的是**真会出问题的地方**，不是挑措辞。每一条都要说清在哪、会怎样出错、怎么改。

## 先弄清审的是什么

- 未提交的改动：`git diff` 和 `git diff --staged`。
- 一个分支：`git diff <基准分支>...HEAD`，再看 `git log <基准分支>..HEAD` 了解每次提交的用意。
- 读改动时，把改到的函数整个读一遍，再看调用它的地方：很多错误不在改的那几行，而在它和周围代码怎么配合。

## 按这个顺序看

1. **对不对**：逻辑错误、边界情况（空的、一个的、很大的、负的、并发的）、错误路径有没有处理、资源有没有释放、改了一处是否漏改了相关的另一处。
2. **安全**：不可信的输入有没有校验、有没有拼接成命令或 SQL、密钥有没有写进代码或日志。
3. **测试**：新的行为有没有测试；改了行为的，旧测试有没有跟着改；测试是在验证行为，还是只在复述实现。
4. **和项目约定是否一致**：命名、错误处理方式、目录结构，照仓库里已有的写法比。
5. **能不能更简单**：重复的代码、没必要的抽象、已有的工具函数没用上。这一类放在最后，标明是建议。

## 怎么写结果

- 按严重程度排：会出错的在前，建议在后。
- 每条写：文件和行号，问题是什么，在什么输入或情况下会出错，建议怎么改。
- 拿不准的标成"疑问"，说出你的推测，不要当成定论。
- 没发现问题就直说没发现，并说明你看了哪些方面。不要为了凑数挑小毛病。
- 用户只要审查的，只看不改。
