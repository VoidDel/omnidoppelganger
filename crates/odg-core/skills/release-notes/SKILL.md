# 写发布说明

发布说明是写给使用者的，不是写给开发者的提交清单。使用者想知道的是：有什么新东西，什么变了，我要不要做点什么。

## 收集变化

- 确定范围：上一个版本的标签到现在，`git log <上个标签>..HEAD --oneline`；需要细节时看合并请求的说明和 diff。
- 看项目已有的 `CHANGELOG.md` 或往期发布说明，照它的格式、语言和分类写。没有的话用常见的 Keep a Changelog 格式。

## 挑和归类

- 只留使用者看得到、用得上的变化。纯内部的重构、测试、CI 调整、依赖的小升级，一般不写，或者合成一句。
- 按影响归类：
  - **不兼容的变化**：放最前面，说清楚要怎么迁移。
  - **新功能**
  - **改进**
  - **修复**：写修好了什么现象，而不是改了哪个函数。
- 几次提交做的是同一件事的，合成一条。

## 怎么写每一条

- 用使用者的话写，说结果：「现在可以把 PDF 附在消息上」，而不是「新增 pdf.rs 模块」。
- 一条一句，必要时补半句为什么、怎么用。
- 有对应的 issue 或合并请求编号，照项目习惯附上。
- 拿不准某个变化对使用者有没有影响的，问用户，不要猜。

## 完成之后

把草稿给用户看。不要自己打标签、发版或推送，除非用户明确要求。
