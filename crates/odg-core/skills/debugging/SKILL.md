# 系统排错

凭感觉改、改了再看，往往越改越乱。按下面的步骤走，每一步都有证据。

## 1. 复现

- 先让问题稳定地出现：找到最短的触发步骤、命令或输入。能写成一个失败的测试最好，它以后还能防止问题再犯。
- 记下实际看到的和期望看到的：完整的报错、堆栈、退出码、输出。不要只看最后一行。
- 复现不了的，先弄清环境差异（版本、配置、数据、并发、时序），而不是猜着改。

## 2. 缩小范围

- 从报错的位置往回读调用链，弄清数据是在哪一步变得不对的。
- 能二分就二分：在中间加日志或断言，看错误在哪一半；问题是最近才出现的，用 `git log`、`git bisect` 找出是哪次提交引入的。
- 一次只改一个变量。

## 3. 提出假设并验证

- 把怀疑说成一句可以检验的话（"X 在 Y 为空时返回了 null"），然后用最小的实验去证实或推翻它：加一行日志、跑一个小例子、读一段源码。
- 推翻了就换下一个，不要硬改到看起来能跑。
- 依赖库的行为拿不准时，去读它的源码或文档，不要凭印象。

## 4. 修根因

- 修在错误产生的地方，而不是出现症状的地方：补一个判空让报错消失，不等于修好了。
- 想一想同样的错误在别处有没有：同一个函数的其他调用者、同样写法的其他代码。
- 修完跑复现步骤确认好了，再跑相关测试确认没有弄坏别的。临时加的日志和调试代码要删掉。

## 汇报

说清楚：原因是什么、证据是什么、改了哪里、怎么验证的。没找到根因的，就说没找到，列出已经排除的和还剩的可能。
