# 安全审查

安全问题的核心是：**不可信的数据，能不能走到它不该去的地方**。从数据的来源追到它的用处。

## 先画出边界

- 哪些输入不可信：网络请求、用户上传的文件、命令行参数、环境变量、读进来的配置和数据、第三方接口的返回，以及模型生成的内容。
- 哪些地方危险：执行命令、拼 SQL、读写文件路径、渲染 HTML、反序列化、发出网络请求、权限判断、写日志。
- 审查时沿着"不可信输入 → 危险用处"这条线读代码，每条线上有没有校验、转义、限制。

## 重点看

- **注入**：命令、SQL、模板、正则、HTML 里有没有直接拼进不可信的内容；该用参数化、转义或白名单的地方有没有用。
- **路径**：用户给的路径有没有 `..`、绝对路径、符号链接逃出预期的目录。
- **权限**：每个操作有没有检查调用者能不能做；能不能改一个 ID 就看到或改动别人的数据。
- **密钥和敏感数据**：有没有写进代码、配置、日志、错误信息、提交历史；传输和存储有没有保护。
- **默认值**：调试开关、宽松的跨域、默认口令、过大的权限、没有上限的大小和次数。
- **依赖**：有没有已知漏洞的版本（项目有 `npm audit`、`cargo audit` 一类工具就跑一下）。

## 怎么写结果

- 每条写：在哪（文件和行号）、怎么被利用（给出具体的输入或步骤）、后果多严重、怎么修。
- 按严重程度排。拿不准能不能被利用的，标成"需确认"，说明你的推理。
- 不要为了验证漏洞去攻击真实的系统或外部服务；需要演示的，在本地和测试数据上做。
- 只审查不改，除非用户要你修。
