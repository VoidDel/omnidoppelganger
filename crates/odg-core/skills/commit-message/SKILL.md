# 写提交说明

提交说明是写给以后读 `git log` 的人的：他们看得到改了什么（diff 里都有），看不到为什么改。说明要补上这一块。

## 先看清要提交的是什么

1. `git status` 看哪些文件改了、哪些已暂存。只提交用户要提交的；没暂存的、和这件事无关的，不要顺手带上。
2. `git diff --staged`（还没暂存就看 `git diff`）读一遍改动本身，不要只凭记忆写。
3. `git log --oneline -15` 看这个仓库的习惯：用中文还是英文，标题有没有 `feat:`/`fix:` 这类前缀，标题用祈使句还是陈述句，多长。照着它写，不要另起一套。

## 怎么写

- **标题一行**，说这次提交做成了什么，不超过 72 个字符（中文约 36 个字），末尾不加句号。用仓库的习惯；没有习惯可循时，英文用祈使句（`Fix …`、`Add …`），中文用动宾短语（"修复……"、"增加……"）。
- **空一行，再写正文**，说为什么：原来哪里不对、为什么选这个改法、有没有放弃的别的做法。改动很小、标题已经说清楚的，可以不写正文。
- 一次提交只做一件事。改动里混着不相干的几件事，先告诉用户，建议拆开提交。
- 不要写"更新了文件 X"这种 diff 里一眼就能看到的话；不要写"修复了一些问题"这种说了等于没说的话。
- 有关联的 issue 或工单号，照仓库习惯写在标题或正文末尾。

## 提交

- 用户只是要说明的，把写好的说明给他看，不要自己提交。
- 用户让你提交的，提交前确认暂存的内容就是要提交的那些；提交后用 `git log -1 --stat` 核对一遍。
- 不要用 `--no-verify` 跳过钩子，除非用户明确要求。钩子失败了，先看它报什么。
