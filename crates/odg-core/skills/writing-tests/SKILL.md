# 写测试

好的测试在代码坏掉时失败，在代码没坏时不失败，失败时让人一眼看出坏在哪。

## 先看项目怎么测

- 找到已有的测试：测试文件放在哪、叫什么、用什么框架、怎么跑（看 `package.json`、`Cargo.toml`、`pyproject.toml`、CI 配置或 README）。
- 照着已有测试的风格写：断言的写法、测试数据怎么准备、有没有共用的辅助函数。不要另引一个测试框架。

## 测什么

- **测行为，不测实现**：通过公开的接口输入、检查输出和可见的效果。测试不应因为内部重构而失败。
- 每个测试一件事，名字说清楚它验证的是什么（"空列表返回零"，而不是"测试一"）。
- 覆盖这些情形：正常的输入；边界（空、一个、最大、零、负数、很长的字符串、非 ASCII）；出错的输入和出错的路径；修 bug 时，那个 bug 的触发条件。
- 外部依赖（网络、时钟、随机数、文件系统）尽量隔离：用临时目录、固定的时间、项目已有的替身，而不是真的发请求。

## 确认测试有用

- 写完先跑一遍，看它通过。
- 再想办法让它失败一次：把被测代码临时改坏，或者在修 bug 之前先跑，确认测试确实会失败、失败信息说得清楚。一个从来不会失败的测试没有用。
- 跑一遍整套相关测试，确认没有弄坏别的；测试之间不应该互相依赖执行顺序。

## 汇报

列出加了哪些测试、各验证什么、怎么跑；有没覆盖到的情形，说出来。
